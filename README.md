# dz-bet — المرحلة 0

هذا المستودع ينفّذ **بوابة التحقق المزدوج** قبل بناء أي معمارية تنبؤية متقدمة. لا يعلن النظام وجود إشارة قبل تشغيل باكتيست زمني على بيانات حقيقية، مع إبقاء آخر موسم كامل معزولًا كـ hold-out.

## النطاق المنفّذ

| المسار | التنفيذ الحالي | الحالة |
|---|---|---|
| A — Predictive Baseline | نموذج Poisson مبني على أهداف home/away، وتقدير احتمالات 1X2، وقياس ROI مقابل closing odds | جاهز للتشغيل |
| B1 — Sharp Line Monitoring | كشف تحرك سعري أكبر من العتبة على سجل odds timestamp-aligned | جاهز للتشغيل |
| B2/B3 — OSINT | مخطط إدخال نصوص ومصادر وTeam Stability Score مع منع خلطها مع نتائج المباريات | واجهة أولية، بلا ادعاء إشارة |
| Confluence | مصفوفة قرار قابلة لإعادة الإنتاج مع عتبات محددة في الإعدادات | جاهز للتشغيل |
| Devil’s Advocate | فحوص مضادة تمنع اعتبار العينة الصغيرة أو التسرب الزمني دليلًا | جاهز للتشغيل |

## التشغيل

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
python -m dzbet.cli validate --matches data/raw/matches.csv --odds data/raw/odds.csv
python -m dzbet.cli backtest --matches data/raw/matches.csv --odds data/raw/odds.csv --out reports/phase0.json
```

يمكن تنزيل بيانات مباريات حقيقية من مصدر موثق ثم وضعها في `data/raw/`. لا توجد بيانات تحليلية مزيفة في المستودع. القالبان يوضحان العقد المطلوب فقط.

## سياسة البيانات

يجب أن تحتوي بيانات المباريات على `match_id,date,home_team,away_team,home_goals,away_goals,season`. يجب أن تحتوي بيانات odds على `match_id,bookmaker,market,selection,odds,timestamp`. يرفض المدقق التكرارات، الأسعار غير الصالحة، والمباريات التي لا يمكن ربطها زمنيًا.

يقسم النظام البيانات زمنيًا إلى تدريب، اختبار، وhold-out. لا يجوز استخدام hold-out لاختيار العتبات أو تحسين النموذج. لا تُعرض نتيجة المرحلة بوصفها إشارة قابلة للاستغلال إلا بعد تحقق معايير البوابة في تقرير مكتمل.

## قرار المرحلة 0

النظام **متوقف عمدًا قبل الانتقال إلى أي خطوط إنتاجية أو مرحلة لاحقة**. نقطة التحقق المطلوبة هي تقرير `reports/phase0.json` الناتج من بيانات حقيقية، ويجب أن يثبت أداء المسارين منفردين، أداء التقاطع، وعدد الحالات ومجال عدم اليقين.
